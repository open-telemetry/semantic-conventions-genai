# Realtime voice span vs. Chat (inference) span — similarities, differences, and required attributes

Non-normative design analysis for PR #394 (realtime voice instrumentation). Grounds the
discussion on @lmolkova's review point: *"whether we should use inference/chat span to
describe realtime… I think we need a new span type and definitely some new operation names.
Reuse attributes and message types as much as makes sense, but we should limit this new
span to only the attributes that are applicable to it."*

Source of truth for the existing chat span: `model/gen-ai/spans.yaml`
(`gen_ai.inference.client`) and `model/gen-ai/registry.yaml`.

---

## 1. TL;DR

- The **per-turn** realtime span overlaps heavily with the chat inference span (model,
  usage, input/output messages, output type). Reuse of **attributes and message types**
  is the right instinct.
- **Audio is shared, not distinguishing.** Chat Completions already does audio in/out with
  audio models (`gpt-4o-audio-preview`, PR #393), so the audio message parts and
  `gen_ai.usage.audio.*` tokens are common ground. The real realtime differentiator is the
  **live session**: streaming both ways, server-side **turn detection / VAD**, and
  **barge-in**.
- But `operation.name = "chat"` is a **semantic mislabel**, and the chat span definition
  carries **inapplicable required/recommended attributes** while **missing** the genuinely
  realtime-only concepts (**turn detection / VAD, session correlation**; voice + audio
  format are shared with audio chat).
- Recommended shape: **per-turn span** (not a session-length span) with a **new
  operation name** and a **tailored attribute set**. A long-lived **session** is modeled
  as a **correlating id / entity**, not a wrapping span.

---

## 2. Conceptual comparison

| Dimension | chat / inference | realtime (voice) |
|---|---|---|
| Transport | One request → one response (HTTP) | Long-lived bidirectional **WebSocket session** |
| Statefulness | Stateless, single turn per call | Stateful, **many turns** over one connection |
| Streaming | Optional token stream for one response | **Always** streaming; audio chunks **both directions**, interleaved |
| Turn boundary | Explicit (client sends request, reads response) | **Server-side VAD / turn detection**; supports **barge-in / interruption** |
| Output | text / structured / image / **audio** (with audio models, e.g. `gpt-4o-audio-preview`) | **speech** (audio blob) **+ transcript** |
| Config timing | Per-call request params | Session defaults **±** per-turn overrides (provider-dependent, see §5) |
| Operation semantics | text/multimodal completion (incl. audio in/out) | speech-to-speech **turn within a live session** |

> **Audio modality is NOT the differentiator.** OpenAI **Chat Completions** already
> supports **audio input and audio output** with audio models (e.g.
> `gpt-4o-audio-preview`): `modalities: ["text","audio"]`, `input_audio` content parts,
> `message.audio` output, and audio token usage (this is the PR #393 case). So the shared
> pieces — **audio message parts** and **`gen_ai.usage.audio.*` tokens** — belong to the
> common/chat surface, not to realtime specifically. What actually separates realtime is
> the **live session**: statefulness, always-on bidirectional streaming, **server-side
> turn detection / VAD**, and **barge-in / interruption** — none of which the single-shot
> chat request has.

> **Output transcript is also shared, not realtime-only.** Verified in the installed SDK:
> `ChatCompletionAudio` (`openai/types/chat/chat_completion_audio.py`) has a
> `transcript: str` field ("Transcript of the audio generated by the model"). So audio
> **Chat Completions returns an output transcript** in `message.audio.transcript` — the same
> normalized "audio blob + transcript" shape as realtime. Direction nuance: **output → transcript**
> is available for **both** audio chat and realtime; **input → transcript** is realtime-only
> (`input_audio_transcription` config/events; chat completions does not return an input
> transcript). This is direct ammunition for comment **r3669354515** — the audio-part
> `transcript` is a **shared audio-modality concept** (populated by audio chat *and*
> realtime), supporting (a) keeping it on the common message-part model and (b) restricting
> it to `modality = audio` via the JSON-Schema `if`/`else` conditional.

## 3. Span boundary decision: per-turn, not per-session

A realtime session (WebSocket) can stay open **minutes to hours** and is **mostly idle**
(waiting for the user to speak). A session-length span is an anti-pattern:

- Cannot be exported until the session **ends**; a crash loses the whole span.
- Its duration measures **connection lifetime, not model work** — useless as a latency
  signal.
- Very long spans are poorly handled by most tracing backends.

OTel generally does **not** span long-lived connections (HTTP keep-alive, DB connections,
messaging consumers); it spans the **operations that flow over** them.

**Decision:** the primary span is **one model turn/response** (crisp start/end via turn
detection / `response.done`). The **session** is a **correlating identifier**
(`gen_ai.conversation.id` or a session id) + optional connect-time **entity/event** for
session config. **No** long-lived session span.

This answers @lmolkova's two inline questions:
- *"How would instrumentation know when to start/end this span?"* → per **turn**.
- *"Anything important to capture about the session itself?"* → yes, as **id + attributes/
  entity**, not a wrapping span.

### 4d. Add (new realtime-specific concepts, not in chat span today)

These would need new registry attributes. **Note:** `voice`, `audio format`, and
`modalities` are **also present in audio Chat Completions** (`gpt-4o-audio-preview`:
`audio: {voice, format}`, `modalities`), so they are really **shared audio-chat concepts**,
not realtime-only — they should be defined once and reused by both audio chat and realtime.
The **genuinely realtime-only** concepts are **session correlation** and **turn detection /
VAD**.

| Proposed concept | Realtime-only? | Purpose | Provider mapping (verified in SDKs) |
|---|---|---|---|
| Session id | **Yes** | Correlate turns in one WebSocket session | OpenAI session id; Gemini `session_resumption` handle |
| Turn-detection / VAD | **Yes** | Turn-taking / barge-in config (**session-level only** — not a per-turn attribute; see §4d-1) | OpenAI `turn_detection` (in `audio`); Gemini `explicit_vad_signal` + `realtime_input_config` |
| Input-audio transcription | **Yes** | Config/events to transcribe the **user's** spoken input (chat completions does **not** return an input transcript) | OpenAI `input_audio_transcription` + events; Gemini `input_audio_transcription` |
| Output-audio transcript | Shared w/ audio chat | Transcript of the **model's** spoken output (carried by the `transcript` message-part field) | OpenAI `ChatCompletionAudio.transcript` / realtime transcript events; Gemini `output_audio_transcription` |
| Voice | Shared w/ audio chat | Output voice identity | OpenAI `voice` (e.g. `alloy`); Gemini `speech_config` voice |
| Audio format / encoding | Shared w/ audio chat | In/out audio encoding | OpenAI `input/output_audio_format` / `audio.format`; Gemini audio config |
| Modalities | Shared w/ audio chat | Configured output modalities | OpenAI `output_modalities`; Gemini `response_modalities` |

> Naming for these is TBD and should follow OTel naming guidance; several may be captured
> **once per session** (entity/event) rather than repeated on every turn span.

> **Output transcript** is listed as **shared with audio chat** (`ChatCompletionAudio.transcript`,
> §2), not realtime-only. It is carried by the `transcript` field on the audio message part
> (comment r3669354515) rather than a new realtime attribute. Only the **input**-audio
> transcription (transcribing the user's speech) is realtime-only.

### 4d-1. Deep dive: turn detection / VAD

**Voice Activity Detection (VAD)** is how the server decides **when the user starts and
stops speaking** in the continuous audio stream. It drives three realtime-only behaviors
that have **no equivalent in chat completions**:

1. **Turn segmentation** — commit the buffered user audio as one complete utterance.
2. **Auto-response** — trigger a model reply once speech stops.
3. **Barge-in / interruption** — cancel the model's in-progress response when the user
   starts speaking over it.

Verified config (installed SDKs):

**OpenAI Realtime — `turn_detection`** (`RealtimeAudioInputTurnDetection`, a discriminated
union in `audio.input`):

- `server_vad` (acoustic/silence): `threshold` (0.0–1.0, default 0.5), `prefix_padding_ms`
  (default 300), `silence_duration_ms` (default 500), `create_response` (auto-reply on
  stop), `interrupt_response` (barge-in), `idle_timeout_ms`.
- `semantic_vad` (model decides end-of-turn): `eagerness` (`low`/`medium`/`high`/`auto`;
  max waits 8s/4s/2s), `create_response`, `interrupt_response`.
- `null` → automatic detection **off**; client manually commits the buffer and requests a
  response.

**Gemini Live — `realtime_input_config`** (+ `explicit_vad_signal` on `LiveConnectConfig`):

- `automatic_activity_detection`: `disabled` (bool), `start_of_speech_sensitivity`
  (`HIGH`/`LOW`), `end_of_speech_sensitivity` (`HIGH`/`LOW`), `prefix_padding_ms`,
  `silence_duration_ms`.
- `activity_handling`: `START_OF_ACTIVITY_INTERRUPTS` (barge-in) / `NO_INTERRUPTION`.
- `turn_coverage`: `TURN_INCLUDES_ONLY_ACTIVITY` / `TURN_INCLUDES_ALL_INPUT`.
- `explicit_vad_signal` (bool) → client sends explicit speech start/end (manual mode).

**Cross-provider common primitives** (despite different names, both converge):

| Concept | OpenAI | Gemini |
|---|---|---|
| Auto vs manual | `turn_detection = null` vs set | `automatic_activity_detection.disabled` / `explicit_vad_signal` |
| Detection strategy | `server_vad` vs `semantic_vad` | acoustic sensitivity (no semantic mode) |
| Pre-speech padding | `prefix_padding_ms` | `prefix_padding_ms` |
| Silence to end turn | `silence_duration_ms` | `silence_duration_ms` |
| Sensitivity | `threshold` (0–1) | `start`/`end_of_speech_sensitivity` (HIGH/LOW) |
| Barge-in | `interrupt_response` | `activity_handling` |

**Attribute recommendation:** standardize only the **shared, low-cardinality** primitives —
e.g. a **turn-detection mode/enabled** attribute (auto vs manual; server vs semantic where
applicable) and optionally a **barge-in enabled** flag. Keep the fine numeric knobs
(`prefix_padding_ms`, `silence_duration_ms`, threshold/sensitivity) **opt-in** — their
types diverge (float `threshold` vs `HIGH`/`LOW` enum) and they're rarely needed for
analysis.

**Placement: session-level only — not a per-turn attribute.** Verified in the SDKs:

- **OpenAI**: `turn_detection` lives on the **session** (`audio.input.turn_detection`, set
  at `session.update`). The per-turn override object `RealtimeResponseCreateParams`
  (`response.create`) exposes only `audio.output` (format + voice) — **no `input`, hence no
  `turn_detection`**. VAD **cannot** be set per response/turn.
- **Gemini**: `realtime_input_config` is on `LiveConnectConfig`, applied **at connect** →
  **session-fixed**, with no per-turn override.

So VAD attributes should be captured **once per session** (connect-time entity/event), **not
repeated on every turn span** — they cannot vary per turn. **Re-emit case:** OpenAI allows a
mid-session `session.update` that changes `turn_detection`; if modeled as a connect-time
event, such an update warrants a **new session-config event**, not a turn-span attribute.

## 5. Config scope differs by provider (affects 4b)

| Config | OpenAI Realtime | Gemini Live |
|---|---|---|
| Scope | Session default (`session.update`) **+ per-response override** (`response.create`) | Session-fixed (`LiveConnectConfig` at connect) |
| `max_output_tokens`, `instructions`, `output_modalities` | Settable **per turn** (response.create) | Fixed for session (new session to change) |
| `temperature` | **Not in GA** (`gpt-realtime`); existed on old `gpt-4o-realtime-preview` | `generation_config.temperature`, fixed for session |
| `voice` | Per turn, but **locked after first audio output** | Fixed for session |
| Sampling (`top_p`/`top_k`/penalties/`seed`/`stop`/`n`) | **Not exposed** | `generation_config`, fixed for session |

Implication: OpenAI's remaining per-response knobs (`max_output_tokens`, `instructions`,
`output_modalities`) map **cleanly onto a per-turn span**; OpenAI has **dropped most
sampling params** in GA. Gemini's params are **session-global** and would be
**inherited/repeated** on each turn span (or captured once at the session level).

Refs (verified against installed SDKs): OpenAI `RealtimeSessionCreateRequestParam`
(openai-python `src/openai/types/realtime/`); Gemini `LiveConnectConfig` + `GenerationConfig`
(google-genai `types.py`, gemini-live `.venv`).

## 6. Operation name

`chat` is a semantic claim (stateless text/multimodal completion). @lmolkova cites OpenAI's
audio API operations as precedent that audio operations get purpose-specific names:

- **transcription** — speech → text, same language (`/v1/audio/transcriptions`)
- **translation** — speech → English text (`/v1/audio/translations`)

These are **precedent, not a proposed label** for realtime. Realtime is speech-to-speech,
so it warrants **its own** operation name. Candidate values (TBD, pick per naming
guidance): `realtime`, `converse`, `speech`, `voice`.

> Concrete backing for the "translation" framing: **Gemini Live's `LiveConnectConfig`
> literally has a `translation_config` field**, and OpenAI has dedicated
> `transcription`/`translation` audio endpoints — reinforcing that audio operations carry
> purpose-specific names rather than `chat`.

## 7. Options summary (the remaining decision)

| Option | operation.name | span definition | attribute set |
|---|---|---|---|
| A. Reuse chat (current PR) | `chat` | `gen_ai.inference.client` | inherits all chat attrs (incl. inapplicable) |
| C. New span type (lmolkova leans here) | new value | **new** `gen_ai.realtime.client` | purpose-built set |

- **A** is what the PR does today — semantic mislabel + inapplicable attributes.
- **C** is the cleanest separation: a dedicated span with only applicable attributes and
  realtime-specific concepts as first-class. It still reuses the shared attribute groups
  (`attributes.gen_ai.common`, `.usage`, `.content`, `.address_and_port`, `.error`), so
  message types / usage / audio tokens stay shared — it just omits the inapplicable
  sampling params instead of inheriting-then-demoting them.

**Recommendation:** **C** — a new `gen_ai.realtime.client` span type with a new operation
name, reusing the shared attribute groups plus the applicable request params, session as a
correlating id, per-turn span. This matches @lmolkova's "new span type… limit to only the
attributes applicable to it."
